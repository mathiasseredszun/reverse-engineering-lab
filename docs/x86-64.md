# x86-64 analysis notes

The captured programs use Linux's System V AMD64 ABI: the first integer or pointer
argument is passed in RDI; an integer result is returned in EAX. Windows x64 uses
a different calling convention. Addresses here are virtual addresses from the
recorded ELF build, not stable addresses in other builds or under ASLR.

In [record_count.asm](../evidence/record_count.asm), find:

```asm
legacy_accept:
    cmp di,0x40
    setbe al
    movzx eax,al
fixed_accept:
    cmp edi,0x40
    setbe al
    movzx eax,al
```

These are excerpts omitting prologue and return instructions. `DI` is the low
16 bits of `RDI`; `EDI` is its low 32 bits. `setbe` materializes the unsigned
below-or-equal comparison. For 65536 (`0x10000`), DI is zero, while EDI is 65536.
That explains the different decisions without relying on the C source alone.

In [token_gate.asm](../evidence/token_gate.asm), correlate the length call,
byte-sized XOR with `0x5a`, data reference and loop branch with the Ghidra export.
The constant is an encoding key, not evidence of cryptographic protection.

The Python ELF reader's `PIE/shared` classification comes from ELF type `ET_DYN`.
That field alone cannot distinguish a PIE executable from every shared object,
prove exploitability, or establish complete hardening. This lab does not present
header parsing as a vulnerability scanner.
